# Frame-rate investigation — 28 September 2026

Baseline: `0.6.33-ui-alignment`, `rgb-staged-startup`, pioarduino 55.03.39 / Arduino 3.3.9 / IDF 5.5.4, LVGL 9.2.2, local smartdisplay 2.1.1. Baseline target build passed after the usual approved external PlatformIO lock retry. This investigation changes no firmware/configuration and performs no upload. No `/dev/ttyUSB*` or `/dev/ttyACM*` port was present; device FPS is not measured.

## Confirmed limits

The complete board profile specifies a 12.5 MHz pixel clock and total line/frame timing of 1056 × 525 (800 × 480 active area). At 16-bit parallel RGB565 this is one pixel per clock, giving a **nominal 22.55 panel scans/s** and a 44.35 ms scan period. This calculation is a configured limit, not a device measurement: the clock divider, rendering duration and progressive single-framebuffer writes affect observed motion.

`include/lv_conf.h` leaves `LV_DEF_REFR_PERIOD` unset; the pinned LVGL 9.2.2 fallback is 33 ms (about 30.3 redraw opportunities/s). The main loop has one tick source and one handler context, with a 1–10 ms bounded sleep. The IDF5 path already excludes the old per-strip 1 ms delay. There is no 60 ms strip-sleep penalty left to remove.

The project adapter creates one **800 × 8 RGB565 internal draw buffer: 12,800 bytes**, partial rendering, synchronous copy into one **768,000-byte PSRAM framebuffer**, and two **800 × 10 internal RGB bounce buffers: 32,000 bytes total**. A whole-screen redraw requires at least 60 full-width render/flush bands. `runtime.cpp` caps framebuffer-copy chunks at 8 rows. The driver continuously scans the framebuffer even when LVGL has no dirty regions.

Existing `[rgb]` diagnostics report flush chunks/pixels and maximum copy/handler/service-gap durations every five seconds. A chunk count is not an FPS count. Pixel count divided by 384,000 gives equivalent full-screen work, not displayed frames. New instrumentation should separately count rendered refreshes containing pixels (last-chunk marker), actual RGB VSYNC/frame completions, total copy time and redraw latency; aggregate counters only in ISR, print from the UI task. Preserve synchronous flush completion ownership.

## Practical optimization order

1. **Remove unchanged layout/style work.** Settings and Firmware render on 250 ms polling. Settings resets long mode/height and lays out caption/value pairs even when content is identical; Firmware reapplies primary action colors/fonts every poll. LVGL 9.2.2 local-style setters refresh the object's style even if callers pass the same value. Cache content/OTA action/theme signatures and relayout/restyle only when changed. Keep countdown/progress/status updates live within the existing 250 ms polling budget. During brightness dragging, `preview_brightness()` also calls the whole `render_appearance_settings()` routine for every value change; update only backlight and percent text during drag, keeping settings persistence on release. Existing Today/Weather/status signatures already avoid much of this work; preserve them. This should reduce redraw bursts and improve available CPU time, but cannot raise the physical scanout ceiling.
2. **Benchmark a 16-row internal draw buffer.** This doubles its allocation to 25,600 bytes (+12,800) and halves full-width LVGL render/flush bands to 30. Keep the existing 8-row copy chunk bound and 10-row RGB bounce buffers initially. Copy calls still number 60, so improvement is limited to rendering traversal/flush overhead; it is not a guaranteed doubling of FPS. Measure largest internal heap block with Wi-Fi/TLS/OTA active before retaining it. A 24-row buffer costs 38,400 bytes and needs separate headroom evidence. Do not apply the generic 1/10-screen buffer suggestion blindly to this RAM-constrained setup.
3. **Evaluate 64-byte data-cache lines in a separate framework build.** The installed Arduino SDK config has 32 KiB DCache with 32-byte lines. Espressif recommends 64-byte lines specifically for RGB bounce-buffer mode. This may improve refill throughput and reduce contention, enabling safer clock headroom. It requires a matching rebuilt framework/SDK or isolated ESP-IDF setup; an application `-D CONFIG_...` flag does not rebuild precompiled framework cache configuration. Retain the recovery package and validate networking, NVS and OTA behavior.
4. **Run a one-variable panel-clock test for higher visible FPS.** Keep all porches, polarities, buffers and driver ownership fixed. A nominal 16 MHz gives 28.86 Hz; **16.632 MHz gives 30 Hz**; 20 MHz gives 36.08 Hz. These are arithmetic targets, not certified panel settings. Establish the panel's supported timing range and stable baseline first, then measure actual VSYNC and inspect the static gray panel test before the full UI with network activity. Driver clock division may produce a different actual rate. Higher PCLK tightens the bounce-refill deadline and can worsen the existing shifts/flicker.
5. **Adjust LVGL redraw period only after rendering/scanout evidence.** A 20 ms period allows up to 50 redraw opportunities/s and may lower input-to-redraw wait or support an increased panel clock, but consumes more CPU if many regions stay dirty. At the current 22.55 Hz scanout it cannot produce 50 visible complete frames/s. Benchmark scrolling/slider latency and redraw duration before/after.

A larger second draw buffer does not automatically parallelize this synchronous CPU-copy path. Full framebuffer double buffering costs at least another 768,000 bytes plus synchronization/copy traffic; it is a separate tearing architecture change, not the first FPS experiment. Previously rejected direct PSRAM DMA and 20-line bounce buffers should not be reused as presumed improvements. CPU is already configured at 240 MHz and PSRAM at 80 MHz Octal; no CPU-frequency uplift remains within the current rated configuration.

## Acceptance measurements

Use the same UI/data/theme, supply, cable and brightness for each variant. Measure a fixed repeated scroll/slider/navigation workload, after service startup and with calendar/weather downloads active: actual scan rate, refreshes containing changed pixels, equivalent screen work, average/worst copy and handler duration, input-to-visible latency, largest internal heap block and visible shifts/tearing. Repeat a static gray test to separate rendering from scanout. Reject any variant that gains throughput while degrading touch, heap headroom, boot, OTA or display stability. Native desktop captures can check correctness and invalidation work; they cannot establish ESP32 FPS.

Recommended first implementation: signature-cache the unchanged Settings/Firmware layout/styles, narrow brightness-drag updates and add accurate frame/latency counters. Then test the 16-row draw-buffer variant. A stable 30 Hz target needs a validated higher panel clock, with the 64-byte cache-line build as a strong candidate to investigate beforehand.
